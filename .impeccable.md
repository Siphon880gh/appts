# Appts design guide

## Design Context

### Users
People managing one or more ongoing medical conditions, often for themselves or a family member. They come back after a visit, a phone call with an insurer, or a letter in the mail, and need to file it quickly. Later they need to answer "what's next?", "who did I see?", and "is that authorization still valid?" under stress. The quality bar is **patient-portal clarity** (MyChart-level: dates, people, and status readable at a glance) on top of the accountability app's craft.

### Brand Personality
Calm, organized, plain-spoken. Use concrete labels ("Valid until Nov 26", "Reorder by", "Rescheduled to") rather than vague statuses. Don't alarm, gamify, or use clinical jargon the user didn't type. Demo data is always marked "(sample)".

### Aesthetic Direction
This inherits the accountability training-log system, retuned for care records:

- Ink/navy: `#172943`. Page: `#f4f3ed`. Paper: `#fffef8`. Secondary text: `#56606e`. Rules: `#d7d9d9`.
- Accent: sky blue `#8cc8f2` (hover `#aad7f7`, soft `#e4f0f8`) with navy text, used for primary actions and "soon" date pills. Deliberately **not** Postop's teal.
- Display: Avenir Next Condensed, Franklin Gothic Medium, Arial Narrow, sans-serif. Body: Avenir Next, Trebuchet MS, sans-serif. Fonts are system-installed only.
- Entry types carry an icon and a color. Badge glyphs use `readableText()`, which picks pure black or white, whichever has more contrast (always at least 4.5:1). The color is never the only cue: the type name or label always appears too.
- Use square-edged ruled lists for records, a big stacked date block (month, day, weekday) on event rows, and relative-day pills ("Today", "In 3 days"). Controls use 4px radii, with no decorative shadows, gradients, or glass.

### Design Principles
1. **What's next comes first.** The overview and condition sidebar lead with Next up: one row per record, the soonest date, and a relative day.
2. **Organize by condition, then by type.** Each condition shows type groups in the order set on the Entry types page, each with its own Add button.
3. **Connected records.** Link fields render as links, backlinks show on the target, and documents link back to their owner.
4. **Never lose data.** Removing fields, archiving types, and changing labels keep the stored values. Destructive actions are rare and explained.
5. **Fit real use.** Keyboard access, visible focus, labelled controls, 390px without overflow, and honest upload and error states are required.

## Implementation constraints
Plain `index.php` plus PHP includes and `api.php`, with no router, Composer/vendor, npm runtime packages, or bundler. Native ES modules power the UI. Data lives server-side per account in guarded `.php` JSON files with atomic writes, `flock`, and backups. Sanitize rich HTML on save (PHP DOM allowlist) and on display. Never render remote images or arbitrary attributes.

## Interaction decisions
- Timeline type chips come from the types present in the current events. Types combine with OR, tags with AND, and there's an explicit "Clear filters".
- Tags are created on the fly from the picker (Enter). Document labels work the same way and are saved for reuse.
- A visit's doctor is optional when the visit kind is "Lab work".
- Navigating via the nav or the hash closes any open dialog.
- The default document label follows the record: a Lab-work visit gives Lab, a visit gives Consultation Note, and a letter gives Insurance Letter.

## Review checklist
- 390px: no horizontal overflow on any view; dialogs fit.
- Every type badge shows its icon, or the placeholder if none is chosen, and its color consistently across lists, timeline, chips, and the Entry types page.
- Use synthetic data only in screenshots. Regenerate them with `sh tests/run-all.sh --screens` when a visual flow changes.
